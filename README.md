# Kaikun 360

> **En une phrase :** une plateforme unique — site web et application — pour
> **acheter, louer, construire, voyager, se déplacer et confier son bien** au
> Sénégal, en toute confiance.

---

## Kaikun 360, c'est quoi ?

Aujourd'hui, une personne qui veut acheter un terrain, louer une maison pour le
week-end, faire construire, réserver une excursion ou louer une voiture avec
chauffeur doit passer par des dizaines d'interlocuteurs différents, sans garantie
de sérieux. **Kaikun 360 rassemble tout ça au même endroit**, avec un principe
central : la **confiance** (biens et prestataires vérifiés, suivi des demandes de
bout en bout, paiement encadré).

### À qui ça s'adresse

La plateforme sépare clairement **cinq types d'utilisateurs**, chacun avec son
espace :

| Utilisateur | Ce qu'il vient faire |
| --- | --- |
| **Client** | Chercher et demander un service : acheter, louer, réserver une nuitée, une voiture, une excursion… |
| **Propriétaire** | Déposer ses biens, les mettre en location, confier leur gestion. |
| **Prestataire** | Proposer ses services (voiture, pirogue, circuit touristique, construction, guide…). |
| **Entreprise** | Organiser des demandes groupées : séminaires, team building, sorties. |
| **Équipe Kaikun** | Piloter la plateforme depuis les coulisses : valider, suivre, encadrer, gérer les paiements. |

### Ce que la plateforme permet (les 9 univers)

| Univers | En clair |
| --- | --- |
| **Immo** | Achat, vente et location mensuelle de biens immobiliers. |
| **Stay** | Location courte durée : nuitées, hébergements meublés. |
| **Manage** | Gestion locative pour propriétaires (loyers, incidents, reversements). |
| **Build** | Construction et rénovation : simulateur de budget, devis, suivi de chantier. |
| **Explore** | Tourisme : circuits, excursions, expériences. |
| **Mobility** | Transport : voiture, navette aéroport, bus, 4×4, pirogue, avec ou sans chauffeur. |
| **Diaspora** | Accompagnement à distance des Sénégalais de l'étranger (vérification, achat, suivi vidéo). |
| **Team Building** | Offres groupées pour entreprises et institutions. |
| **Pro** | Place de marché des prestataires certifiés (inscription, validation, notation). |

## Comment c'est construit

Le projet a **deux grandes parties** :

- **Le « moteur » (backend)** — invisible pour l'utilisateur, c'est le cerveau qui
  stocke les données, applique les règles métier et sécurise tout. Développé avec
  la technologie **Laravel**. Il expose une **API** : une sorte de standard de
  communication que n'importe quel écran (site web, application mobile future)
  peut utiliser.
- **Le « visible » (frontend)** — le **site web** avec lequel l'utilisateur
  interagit réellement. Développé avec la technologie **Angular**.

**Et le mobile ?** L'application mobile native (Play Store / App Store) viendra
plus tard : comme le moteur expose déjà une API standard, elle pourra être ajoutée
**sans rien refaire côté moteur**. En attendant, le site web sera « installable »
sur téléphone (technologie PWA).

### Montrer le site à quelqu'un

```bash
./scripts/demo.sh
```

Une seule commande démarre le moteur, le site et une **adresse publique
temporaire** : le lien s'ouvre depuis n'importe quel téléphone, sans rien
déployer. `Ctrl+C` arrête tout. Le mode d'emploi et les pièges d'une
présentation à distance sont dans [`scripts/README.md`](scripts/README.md).

## Où en est le projet ?

- ✅ **Le moteur (backend) est terminé.** Les 9 univers, les 5 espaces, la
  sécurité, les paiements, les notifications : tout est développé et couvert par
  des tests automatiques. Voir [`backend/README.md`](backend/README.md).
- 🚧 **Le site web (frontend) est en cours.** Le socle graphique et
  l'**authentification** (créer un compte, se connecter, vérifier son compte,
  mot de passe oublié) sont faits. Voir [`frontend/README.md`](frontend/README.md).
- ✅ **Le back-office montre enfin le business en graphiques** (phase F13) : une
  rubrique **Statistiques** réservée aux profils qui ont déjà accès à l'argent —
  revenus mois par mois, d'où vient l'activité, à quelle étape les affaires se
  perdent, et ce qui rapporte le plus. Chaque chiffre est comparé à la période
  précédente, et chaque graphique peut basculer en tableau de valeurs.
- ✅ **Ouverture officielle préparée** (phase F14, hors cahier des charges) :
  une **liste d'attente** à 5 profils (propriétaire, prestataire, client,
  team building, diaspora) recueille les inscrits avant le lancement, et un
  **interrupteur au back-office** peut fermer toute la plateforme au public
  (sauf l'équipe) pendant la préparation — le super administrateur autorise
  ensuite, compte par compte, les personnes qui doivent voir la plateforme en
  avant-première. L'équipe dispose maintenant d'un **écran pour consulter les
  inscrits** (coordonnées et détails saisis, filtrable par catégorie et par
  statut) ; marquer un dossier « traité » **invite automatiquement le prospect
  par e-mail** à créer son compte, avec un message différent selon son profil.
- ✅ **Les e-mails envoyés aux utilisateurs** (bienvenue, code de vérification,
  confirmation de réservation, devis, pièce manquante, invitation à rejoindre
  la plateforme…) ont été entièrement refaits aux couleurs de Kaikun 360 : 27
  messages, un message d'accueil différent pour chaque type de compte. Détail
  en phase F8.8.
- ✅ **Un assistant conversationnel est en place** (phase F10). Il oriente le visiteur
  vers de **vraies** annonces du catalogue, répond aux questions courantes à
  partir de la FAQ tenue par l'équipe, et passe la main à un conseiller quand il
  ne sait pas. Le socle est posé et fonctionne **sans aucun abonnement ni frais** ;
  un moteur plus intelligent pourra être branché ensuite, si le budget est validé.
  **Il est désormais visible** : une bulle en bas à droite, sur tout le site
  public, dans les quatre espaces connectés (F10.1) et jusque dans le back-office
  (F10.3). Connecté, il lit **vos** dossiers (F10.2) ; pour l'équipe, il fait le
  point sur la file de validation, les demandes, les messages, un compte ou un
  règlement — **en lecture seule**, il ne valide et ne rembourse rien. Chacun n'y
  voit que ce que ses droits lui ouvrent déjà à l'écran. **Le moteur intelligent
  est branché** (F10.4) : il suit le fil de la conversation, comprend « et moins
  cher ? », et se coupe tout seul au profit du moteur simple si les clés
  manquent ou si le fournisseur tombe — l'assistant continue de répondre dans
  tous les cas. ⚠️ **Le moteur intelligent est éteint par défaut** : il ne
  s'active qu'avec une clé d'API, donc **aucun frais tant que le client ne l'a
  pas décidé**. ⚠️ Cet assistant **ne figure pas au cahier des charges** : c'est
  un bonus.
- ⏳ **Hors code** (à faire par le client / en parallèle) : nom de domaine,
  hébergement, compte marchand pour les paiements, validation juridique. Détaillé
  en fin de document.

module mais qui ne se pilotent pas pareil — la **flotte** (moyens de transport loués à la journée : voitures, bus, 4x4, pirogues, mise à disposition de chauffeur) et les **départs programmés** (trajets datés réservés à la place). D'où deux onglets. Flotte : tous statuts avec une colonne **conformité** qui est la vraie valeur ajoutée du back-office — assurance manquante, chauffeur non déclaré, pirogue sans gilets se repèrent d'un coup d'œil, le détail des manquements étant en infobulle (la grille reprend celle du `VehicleComplianceChecker` de B7.3, deux jeux d'exigences distincts fluvial / motorisé). Trajets : tous statuts avec le **remplissage** de chaque départ (jauge places prises / restantes, mention « Complet ») — les « disponibilités » du cahier. Ajouts backend : `GET /admin/mobility-services` (remplissage agrégé en une requête via `withSum`, statuts d'annulation dérivés de `BookingStatus::estAnnulee()`) et deux Resources back-office, `AdminVehicleResource` / `AdminMobilityServiceResource` — les champs de contrôle (n° d'assurance, identité du chauffeur) restent **hors** du catalogue public. Comme Catalogues, l'écran est en lecture seule : la décision d'approbation reste concentrée dans l'écran Validation (F7.2.a). **F7.2.k Tourisme** : même logique de découpage — les six éléments du module CDC (« circuits, destinations, programmes, guides, restaurants, capacités groupes ») ne vivent pas au même endroit dans le modèle, d'où **trois onglets**. **Circuits** : capacité groupe en jauge et **programme** rendu par les *inclusions* du circuit (restauration, guide, transport) ; ⚠️ un circuit n'a pas de date de départ, sa capacité est un **total** et le remplissage cumule toutes ses réservations — à ne pas confondre avec le départ daté de Mobilité. **Destinations** : les destinations ne sont pas une entité en base mais une **colonne** des circuits, restituée par agrégation (`GROUP BY`) — couverture, publiés vs en attente, capacité cumulée, fourchette de prix, avec chaînage vers les circuits de la destination. **Guides & restaurants** : servis par la marketplace Pro (`?category=guide,restauration`, filtre multi-valeurs ajouté). **Écart CDC signalé, non comblé** : la plateforme ne connaît guides et restaurants que comme catégories de prestataires et drapeaux d'inclusion — **aucun guide nommé n'est rattaché à un circuit précis** ; le combler demanderait un modèle d'affectation guide ↔ circuit, hors périmètre de la tranche. L'écran l'affiche explicitement plutôt que de le masquer. **F7.2.l Paramètres & contenu** — **dernier des 14 modules du CDC §6**. Quatre onglets, parce que les sept fonctions de la ligne CDC ne se pilotent pas de la même façon. **Réglages** : commissions & marges, coordonnées publiques, et le **barème du simulateur de construction** (les « tarifs ») — un objet imbriqué, aplati en chemins pour être éditable champ par champ sans coder sa structure en dur ; l'enregistrement n'envoie que les clés modifiées, sinon chaque valeur par défaut deviendrait une surcharge en base et un futur ajustement du code n'aurait plus d'effet. **Notifications** : jusqu'ici les canaux étaient codés en dur dans chaque `via()` — impossible de couper le SMS (facturé à l'envoi) sans redéployer. Un point de décision unique (`NotificationSettings`) arbitre désormais : événement coupé → aucun envoi, canal coupé → canal retiré, SMS sans numéro → retiré. ⚠️ Les **codes de vérification et la 2FA en sont exclus** : un réglage capable de verrouiller l'accès à la plateforme n'a pas sa place dans une interface d'administration. **Contenu** : CRUD complet des pages et de la FAQ (le backend existait depuis B13.4, sans écran). **Référentiels** : les **villes** deviennent maintenables par l'équipe (le référentiel était figé depuis les seeders) ; les suppressions sont refusées tant qu'un bien ou un compte est rattaché, et un département non vide est protégé du `cascadeOnDelete` — sans quoi on effacerait des localisations, ou des dizaines de communes, sans le moindre message. **Écart CDC signalé, non comblé** : les **catégories** sont des enums PHP qui portent la logique métier ; l'écran les affiche en lecture seule et l'explique.

> **🎉 F7.4 « Bouclage du back-office » terminé — LE PÉRIMÈTRE EST GELÉ.** Trois derniers items, tous identifiés à l'audit final CDC §6/§7 du 30 juillet 2026, aucun n'étant un module manquant. **F7.4.a Cloisonnement des rubriques par permission** : jusqu'ici un seul `roleGuard` « staff » gardait la racine `/back-office`, et les 16 rubriques du rail s'affichaient pour tout le monde — c'est le serveur qui refusait à l'ouverture. Sûr, mais contraire au CDC §7 qui promet à l'agent Kaikun un « accès financier limité » : il voyait Paiements, Export comptable et Permissions dans son menu et s'y heurtait à un 403. Le rail ne montre plus que les portes qui s'ouvrent, et chaque route porte la garde correspondante. La table de correspondance rubrique → permissions est **partagée** entre le rail et les routes (`backoffice-permissions.ts`) : un lien masqué est aussi une route fermée, jamais l'un sans l'autre — sinon on fabrique soit un lien invisible mais atteignable à l'URL, soit un lien cliquable qui rebondit. Deux partis pris : les écrans de **supervision en lecture seule** (Catalogues, Mobilité, Tourisme) restent ouverts à toute l'équipe — voir sans agir est le métier d'un agent qui prépare un dossier — et **Diaspora** aussi, sa fiche étant gardée côté serveur par « l'agent AFFECTÉ ou un admin » : exiger une permission ici fermerait la porte à celui-là même qui doit entrer. Côté serveur, `UserResource` expose désormais les permissions effectives, mais **uniquement sur son propre compte et seulement à l'équipe** — cette ressource sert aussi aux annuaires admin (une requête par ligne = N+1) et les droits d'un collègue n'ont pas à circuler dans une liste. Le **super_admin** est traité à part : ses droits venant du `Gate::before`, il n'a aucune permission assignée et se serait retrouvé avec le rail le plus vide. ⚠️ **Ceci reste un confort d'interface, PAS la sécurité** : les `can:` des 25 routes `/admin/…` sont inchangés et demeurent la vérité. Un refus renvoie à la Vue d'ensemble avec un message explicite plutôt qu'en silence — une URL en favori qui rebondit sans un mot se lit comme un bug, pas comme un droit manquant. **F7.4.b Écart CDC §7 tranché : l'agent affecte les prestataires.** Le cahier des charges confie explicitement « traitement demandes, validation de base, **affectation prestataire** » à l'agent ; les policies `TeamBuildingRequest::view|manage` et `Provider::assignMission` exigeaient le **rôle admin**. Résultat : la file des demandes entreprises s'ouvrait bien à l'agent (route gardée `consulter:dashboard-admin`) mais chaque fiche répondait 403 — un écran visible et inutilisable. La garde devient la **permission** `traiter:demandes`, donc délégable personne par personne comme tout le reste depuis F7.1.b. L'admin la détient via son rôle : son accès est strictement inchangé. C'est la même correction que celle déjà appliquée aux chantiers en F7.3.e3 (`gerer:chantiers`), l'incohérence entre deux écrans faisant le même geste est levée. **F7.4.c Module Documents complété.** La ligne CDC énumère six familles — « Mandats, contrats, preuves, pièces, rapports, pièces prestataires » — la vue transverse n'en exposait que quatre. Les deux manquantes existaient pourtant en base : les **mandats de gestion** et les **rapports de suivi** (modèle `Report` polymorphe depuis B5.2, donc chantiers ET dossiers diaspora dans la même liste). Aucune migration. ⚠️ **Écart assumé et affiché à l'écran** : un mandat porte ses clauses en **texte** (colonne `terms`), il n'existe pas de PDF signé téléversé — la ligne renvoie vers la fiche du mandat où les clauses se lisent et s'éditent. Stocker un contrat scanné demanderait une table de pièces dédiée, décision produit non prise.

- [x] **Le dossier d'un règlement — l'écran le plus sensible** (`GET /admin/payments/{id}`). Confirmer à tort crédite une réservation jamais payée ; rembourser à tort fait **sortir de l'argent réel**. Ces deux gestes se prenaient depuis une ligne de tableau. La fiche montre d'abord ce qui **prouve** l'encaissement — « complété » n'est pas une preuve, c'est un statut en base : signature du webhook PSP vérifiée, référence PSP, référence de la transaction Wave/OM saisie à la confirmation manuelle. Un bandeau **« encaissement non prouvé »** s'allume quand un règlement est marqué complété sans aucune des deux : exactement ce qu'un contrôle comptable cherchera dans six mois. S'y ajoutent la réservation payée avec son client, et l'**échéancier complet** — un acompte isolé ne veut rien dire, il se lit à côté des autres règlements. **Le remboursement quitte la liste** : irréversible, il ne se décide pas sans la réservation sous les yeux et ne vit plus que dans la fiche ; la confirmation Wave/OM, geste quotidien sans enjeu, y reste. F8.1 et F8.2 ont traité les écrans **trop pauvres** — une ligne de tableau pour décider. Restait le défaut **inverse**, sur les fiches livrées avant : elles avaient toute l'information, empilée à plat. Cinq à sept cartes de même poids visuel, dont des tableaux de douze lignes : sur un mandat, un incident critique ouvert et un reversement jamais exécuté se lisaient au même niveau que les clauses du contrat, six écrans plus bas. Deux mensonges d'écran corrigés au passage — la fiche chantier annonçait l'affectation de prestataires BTP comme « reste à livrer » alors que la section la livrait juste en dessous, et la fiche compte affichait le code brut de l'enum de vérification (« non_verifie »). — _F8.3._
- [x] **Le contenu éditorial s'écrit sans taper de balises** (`shared/components/rich-text-editor/`). Le corps d'une page publique (mentions légales, CGU, à propos) est stocké en HTML et rendu via `[innerHTML]`, mais le back-office n'offrait qu'un `<textarea>` : pour obtenir un titre, l'agent devait écrire lui-même `<h2>…</h2>`. En pratique, deux issues également mauvaises — appeler un développeur pour changer une virgule, ou taper du texte brut qui arrivait en un seul pavé sur le site. L'éditeur remplace la saisie de balises par des boutons (titres, gras/italique, listes, liens, citation) **sans changer le format stocké** : les pages déjà en base s'ouvrent sans conversion et le rendu public est intact. **Aucune dépendance** — `contenteditable` et `execCommand` sont vieux mais universels, là où une bibliothèque d'édition apporterait son propre format de document plus ~150 Ko au premier chargement du site, pour six boutons ; le composant implémente `ControlValueAccessor` et s'utilise avec `[(ngModel)]` comme un champ ordinaire. **L'assainissement a lieu à la source, par liste blanche** : le collé depuis Word est nettoyé à l'entrée et non seulement au rendu, sans quoi la page publique hériterait des styles du traitement de texte. Ce qui n'est pas dans la liste est **déballé** — on garde le texte, on jette la balise : la rédaction n'est jamais perdue. Un `<h1>` devient `<h2>` (le titre de la page en est déjà un), un lien `javascript:` perd son adresse mais garde son libellé, un lien sortant reçoit `rel="noopener"`, et le texte laissé nu est enveloppé dans un `<p>`. La fonction est **idempotente** : une page rouverte dix fois reste identique. La vue « code HTML » reste accessible — elle ne sert plus à écrire, mais la retirer aurait été une régression pour qui sait s'en servir. ⚠️ **La FAQ garde son `<textarea>`, volontairement** : la page publique rend la réponse en texte brut, pas en HTML — y mettre l'éditeur riche ferait apparaître les balises en clair sur le site. 15 tests. — _F8.3._
- [x] **Le client peut enfin payer** (`/mon-espace/reservations/:id/paiement`, `POST /payments/initiate`). Le `Router` est donc résolu **à l'usage**. ⚠️ **Le plan du site est produit par Laravel** (seul à connaître les fiches publiées) mais **relayé par le serveur de rendu Angular** : un moteur n'accepte un `sitemap.xml` que servi par le domaine qu'il décrit, et l'API peut vivre ailleurs. Il applique **exactement les filtres publics** — dont `aVenir()` pour la mobilité, sans quoi le stock toujours croissant de départs passés serait annoncé à Google. **Éprouvé sur le serveur de rendu réel** (`curl` sur les 5 univers) : balises enrichies et JSON-LD **présents dans le HTML envoyé**, espaces privés en `noindex`, `/recherche` hors index, plan du site servi en `application/xml` sous le domaine du site. **8 tests backend neufs** (43 assertions) + **10 vitest neufs** → **65 verts**. — _F9.1 + F9.2._

- [x] **Le rendu serveur pouvait enfin appeler l'API — défaut silencieux né avec le SSR (F2.9).** ⚠️ **En production, `environment.apiUrl` vaut `/api/v1`**, une adresse relative : elle n'a de sens que dans un navigateur, qui la résout contre la page courante. ⚠️ **Cette phase n'est demandée par aucune ligne du CDC** — vérifié par extraction du `.docx` : ni « assistant », ni « chatbot », ni « IA », ni « intelligence artificielle ». - [x] **Le socle : un contrat d'API unique et un cerveau interchangeable.** ⚠️ **Le point de conception qui commande tout le reste : un assistant transverse est une SECONDE PORTE D'ENTRÉE sur toute l'API.** Le risque principal n'est pas qu'il réponde mal, c'est qu'il devienne un **contournement des autorisations** — tout ce qui a été sécurisé de F0 à F9 (validation des annonces, cloisonnement des espaces, policies) redeviendrait négociable en posant une question dans une bulle de discussion. Corollaire moins évident, **le modèle ne voit même pas les adresses des fiches** : l'invite lui interdit d'écrire des liens, mais la façon sûre de tenir cette règle est qu'il n'en ait aucun sous les yeux — une adresse d'espace connecté diffère selon le rôle (le défaut n°1 de F10.1), et un lien recraché de travers envoie la personne sur une page interdite. ⚠️ **On dégrade, on ne casse pas** : clé absente, fournisseur en panne, délai dépassé, réponse vide, refus du modèle → le cerveau déterministe reprend la main **en silence**, avec les mêmes données. Une bulle d'assistant n'est pas l'endroit où afficher une erreur technique à un client, et le moteur simple répond sans clé ni réseau. ⚠️ **La facture est bornée par construction, pas par surveillance** : plafond de tokens **produits** par réponse, et surtout plafond de **tours d'outils** — au dernier tour, les outils sont **retirés** au modèle, qui ne peut alors plus qu'écrire du texte. Une conversation se termine donc toujours, en un nombre d'appels facturés connu d'avance, même si le modèle boucle sur un outil vide (c'est le « déni de portefeuille » vu de l'intérieur : pas un attaquant qui multiplie les messages — le limiteur de débit s'en charge — mais le modèle lui-même). ⚠️ **Le cloisonnement de F10.2 et F10.3 tient sans être réécrit** : le modèle ne reçoit que les outils que le registre lui présente (par rôle pour les espaces, par **permission** pour le back-office), et un outil réclamé hors trousse **ne s'exécute pas** — c'est exactement le scénario de l'injection de prompt réussie, et il ne débloque rien. ⚠️ **Limite connue et documentée** : le point de cache est bien posé sur l'invite système, mais le préfixe minimal cacheable de Haiku 4.5 est de 4 096 tokens, que l'invite et les descriptions d'outils n'atteignent pas — **en pratique aucun cache n'est écrit**, sans erreur ni signal. Le marqueur ne coûte rien et devient utile tel quel si le modèle est monté en gamme. **14 tests neufs (52 assertions)**, exécutés **sans clé et sans le moindre appel réseau** : le transporteur HTTP du SDK est remplacé par un double qui sert des réponses scriptées **et enregistre les requêtes émises** — c'est cette seconde moitié qui rend vérifiable ce qui, autrement, ne l'était pas (que l'historique part bien au modèle, que la trousse transmise est celle du rôle, que les adresses ne sortent jamais du serveur). ⚠️ **Prérequis client, non levé** : un abonnement Claude Pro **ne couvre pas** l'API (produits distincts) — il faut un compte d'organisation sur la Console Anthropic, **au nom du client**, avec un plafond de dépense. Tant que la clé n'existe pas, le driver reste éteint et **la plateforme n'émet aucun appel sortant**. — _F10.4._
- [x] **L'assistant sort du coin bas-droite : un bouton dans l'en-tête, un tiroir sur toute la hauteur.** Travail d'**apparence**, mais qui répare trois gênes constatées à l'écran : la bulle flottante **recouvrait le contenu** de chaque page sans qu'on le lui demande et se disputait ce coin avec le bouton « retour en haut » et le bandeau d'installation ; le panneau **s'ouvrait grand comme un post-it** sur le seul message d'accueil puis grandissait par à-coups à chaque réponse ; et ses 380 px ne laissaient à une réponse de cinq annonces que la place de les **empiler**, ce qui poussait la conversation hors de vue. Livré : un `assistant-launcher` posé dans les **trois** en-têtes (public, espaces connectés, back-office) et le panneau devenu **tiroir** — 480 px, toute la hauteur, angles arrondis, voile de fond cliquable. ⚠️ **Les deux composants ne se connaissent pas** : ils partagent `estOuvert` sur le store. C'est ce qui permet de poser le bouton dans trois chromes différents sans qu'aucun ne monte le tiroir, ni ne le monte deux fois. ⚠️ **Les résultats défilent désormais en RANGÉE**, et le défilement est celui du **navigateur** (`overflow-x` + `scroll-snap`) : glissement au doigt, molette inclinée, tabulation — tout marche sans une ligne de JS, et l'écoute posée hors zone Angular fait qu'un glissement ne déclenche **aucun cycle de détection**, ce qui compte sur un téléphone modeste. La FAQ, elle, reste empilée : une réponse se lit, elle ne se parcourt pas en cartes de 190 px. ⚠️ **Un défaut d'ergonomie du site ENTIER trouvé en tirant sur ce fil, et c'est le vrai gain de la tranche.** « Voir toutes les annonces » depuis une page longue déposait le visiteur **dans le footer** du catalogue. Deux causes empilées, chronomètre à l'appui : (1) `styles/_base.scss` pose `scroll-behavior: smooth` sur `html`, si bien que toute remontée programmée était **animée** — une glissade lente de 4 000 px à travers la page ; (2) elle se déclenchait à l'**arrivée**, alors que la page d'arrivée s'affiche d'abord **vide**, donc bien plus courte : le navigateur écrête la position au nouveau maximum, c'est-à-dire le bas de cette page provisoire. Mesuré avant correction : `+150 ms → scrollY=514, page=1416 px, 0 carte, footer visible`. La remontée part maintenant de `NavigationStart` et passe par `behavior: 'instant'` ; l'ancre garde sa glissade, là c'est le geste demandé. **Ce n'était pas l'assistant** — n'importe quel lien quittant une page longue avait le défaut ; l'assistant le rendait seulement visible, parce qu'on l'ouvre souvent après avoir défilé. ⚠️ Dans l'en-tête public, « Mon espace » et « Déconnexion » sont **repliés dans un menu** : à deux boutons pleins, la barre débordait et la navigation se cassait en deux lignes. Il s'ouvre **au clic** et non au survol, contrairement aux méga-menus — un menu qui contient « Déconnexion » ne doit pas se déplier parce que la souris passait par là. Vérifié au navigateur piloté (avant/après), builds dev et prod verts, **80 tests vitest** au vert. — _F10.5._

### Phase F11 — Habillage des cadres de navigation

Travail d'**apparence uniquement** : aucune règle métier, aucun appel serveur,
aucun droit d'accès touchés. Les cadres (rails, barres, en-tête) sont ce que
l'utilisateur voit à chaque écran de la plateforme — ils avaient été posés au
fil des phases, chacun dans son coin, sans passe d'ensemble.

- [x] **Les rails se replient, et les cadres deviennent des surfaces arrondies.** Deux gestes, sur les deux shells : le **poste de commandement** (`layouts/backoffice-layout/`) et le **shell partagé des quatre espaces** (`layouts/space-layout/`, client / propriétaire / prestataire / entreprise — une seule modification les couvre tous). **(1) Le pli.** Une poignée ronde à cheval sur le bord droit du rail le fait passer de 260px à 76px : les libellés s'en vont, les icônes restent, **toutes les rubriques restent en place, cliquables et dans le même ordre** — on ne perd jamais le fil de la navigation en repliant. Le choix est mémorisé en `localStorage` (préférence de **poste**, pas de session), avec des clés **distinctes** par shell : vingt rubriques au back-office et cinq dans un espace client ne se replient pas aux mêmes moments. ⚠️ **Les libellés sont masqués par `display: none`, jamais par une opacité** — une opacité les laisserait occuper la place et imposer une largeur minimale au lien, qui refuserait alors de descendre à 76px. ⚠️ **Le pli est neutralisé sous le seuil mobile** : là, le rail est un **tiroir** commandé par le hamburger, et un tiroir à 76px n'aurait aucun sens — on l'ouvre pour lire, pas pour deviner ; la préférence reste mémorisée et reprend sur grand écran. ⚠️ **Ce que le pli fait disparaître doit se retrouver ailleurs** : chaque rubrique reçoit une infobulle (et **seulement** repliée — déplié, le libellé est déjà écrit à côté), la pastille de non-lus devient un **point cerné** posé sur l'angle de l'icône dont le compte exact reste dans l'`aria-label` du lien, et les trois entrées de pied du back-office (« Mon compte », « Retour au site », « Se déconnecter »), jusque-là de simples lignes de texte, ont reçu des icônes — sans quoi le rail replié n'en aurait plus rien montré. ⚠️ **Dans le shell des espaces, la classe du pli est portée par `.account-app` et non par le rail** : le rail y est en `position: fixed`, c'est la marge de `.account-body` qui lui fait sa place, et les deux doivent bouger ensemble — une classe sur le seul rail aurait laissé un trou de 200px entre le menu replié et le contenu. **(2) Les surfaces.** Le back-office devient **deux cartes** (rail + colonne de contenu) posées sur son fond graphite avec 12px de gouttière ; les espaces gardent leur rail fixe mais décollé des bords, et leur barre supérieure devient une carte arrondie ; l'en-tête du site public reste **collé en haut et sur les côtés**, seuls ses deux coins **bas** s'arrondissant — un bandeau qui retombe sur la page plutôt qu'une carte posée dessus. ⚠️ **Aucun `overflow: hidden` sur un rail ni sur une barre, malgré la tentation de « faire propre » aux angles** : la poignée de pli déborde volontairement du bord droit et serait rognée, et surtout le menu utilisateur et le panneau de notifications sont **en position absolue dans** la barre des espaces — ils retombent sous son bord bas et auraient été tranchés net. Le défilement interne du rail, qui garde son pied atteignable sur un écran bas, est descendu sur la seule zone de navigation. ⚠️ **Le fond de l'en-tête public reste translucide et son flou conservé** : c'est ce qui laisse le contenu défiler visiblement derrière lui ; l'opacifier « pour faire propre » lui aurait retiré ce qui le rend vivant. À l'inverse la barre des espaces **doit** être opaque et porter sa gouttière sur son hôte — collée en haut, elle laisserait sinon voir le contenu remonter dans les 12px au-dessus d'elle. ⚠️ **Un défaut visuel diagnostiqué à contre-emploi, à retenir** : un « angle droit dans le coin arrondi » signalé sur la barre des espaces ne venait **pas** du coin. L'ombre portée du rail déborde sur la gouttière, et la barre — collante et opaque — repeint son rectangle par-dessus et **tranche cette ombre net sur son bord gauche, qui est droit**. C'est cette coupure qu'on voyait. Corrigé en ramenant l'ombre du rail au même niveau discret que celle de la barre : un rail bleu nuit sur du crème se détache de toute façon par sa seule couleur. ⚠️ La poignée de pli est calée à **82px** dans les deux shells — les 69px du bandeau de marque plus une respiration, hauteur qui est **aussi** celle de la barre supérieure : elle tombe donc à la fois sous le coin arrondi de la barre (qu'elle mordait) et sur la couture du bandeau de marque. Un seul chiffre, deux alignements ; le changer suppose de vérifier les deux hauteurs. Au passage, le **halo bleu du hero** de l'accueil a été retiré : posé en `--k-brand-050`, une couleur **opaque**, il ne teintait pas le crème dans son dégradé radial, il le **remplaçait** — d'où un coin franchement bleu, lu comme un aplat plutôt que comme une lueur. ⚠️ Ne pas le rétablir en touchant à ce jeton, qui sert à une septantaine d'endroits comme fond bleuté **plein**, où l'opacité est justement ce qu'on attend. — _F11.1._

- [x] **Les cartes de l'accueil sortent du rectangle arrondi que font toutes les applications.** Demande du client : la page d'accueil était *lisible mais banale* — mêmes cartes, même rayon, même ombre du hero au pied de page, donc **rien ne hiérarchise et rien n'accroche**. ⚠️ **La déformation a été écartée**, et l'arbitrage mérite d'être connu : angles cassés, cartes penchées, formes organiques fonctionnent en portfolio et jouent **contre** un produit dont toute la promesse est *vérifié, suivi, tracé* — quelqu'un qui engage 45 millions sur un bien qu'il ne peut pas visiter cherche des signes de sérieux, et ces formes datent un site en deux ans. La différenciation passe donc par la **matière et le mouvement**, pas par la géométrie. Cinq traitements ont été maquettés côte à côte avec les vraies couleurs et la vraie typographie ; le client a choisi **l'icône qui déborde**, appliquée aux **trois grilles** de l'accueil (Univers ×9, Protocole ×3, Services ×4) : la pastille sort du cadre par le haut, la carte reste un rectangle parfaitement lisible, mais la grille cesse d'être plate — l'œil accroche la ligne de pastilles avant de lire un mot. ⚠️ **La pastille s'oppose toujours à son fond, et l'inversion n'est pas décorative** : bleu nuit sur les sections claires, **or sur la section navy** — où une pastille sombre serait invisible à la fois sur le fond et sur la carte, qui n'est qu'un voile blanc à 4 %. Au survol elle se soulève, bascule de 6° et prend la couleur d'accent de sa section (bleu de marque, vert, or éclairci) : le sombre **pose**, l'accent **répond**. ⚠️ **Le débordement a d'abord été impossible, et la raison est instructive** : la carte des univers portait un `overflow: hidden` — indispensable pour contenir le reflet diagonal qui la balaie au survol — qui aurait **tranché l'icône**. Le rognage est descendu dans un élément dédié (`.univers-shine`) qui épouse la carte, si bien que le reflet reste borné aux coins arrondis pendant que l'icône sort librement ; l'effet existant est conservé à l'identique, toujours animé par `transform`. ⚠️ **Un piège de cascade qui aurait tout annulé en silence** : une règle écrite plus bas dans le fichier posait `position: relative` sur l'icône ; à spécificité égale elle l'emportait sur le `position: absolute`, la pastille retombait dans le flux et cessait de déborder — **sans qu'aucune erreur ne le signale**. L'icône est désormais traitée à part, avec l'avertissement en clair. ⚠️ **Les gouttières des grilles sont devenues DISSYMÉTRIQUES** (`gap: 48px 20px`), et c'est un calcul, pas un goût : la pastille remonte de 22px et son ombre déborde d'une quinzaine de pixels au-dessus d'elle, soit près de **36px hors de la carte** — dans les 20px d'origine elle mordait la carte de la rangée supérieure. Seules les gouttières horizontales sont concernées, l'icône ne dépassant que par le haut. ⚠️ **Effet de bord traité** : les cartes Services sont des **cibles d'ancre** (liens venus des méga-menus) ; leur `scroll-margin-top` est passé de 90 à 116px, sinon l'arrivée coupait la pastille. Sous `prefers-reduced-motion`, les trois grilles cessent de basculer — seule la couleur répond. **80 vitest verts.** — _F11.2._

Le fichier est l'**original** récupéré sur `paytech.sn`, redimensionné à 3× sa taille d'affichage (écrans à haute densité), rangé dans `frontend/public/partenaires/`. ⚠️ **Chemin ABSOLU (`/partenaires/…`)** : en relatif, une route imbriquée comme `/mon-espace/reservations/12/paiement` l'aurait cherché dans `/mon-espace/reservations/12/partenaires/` — un 404 invisible en développement. ⚠️ **`alt` vide + `aria-hidden`** : le mot « PayTech » est déjà écrit juste à côté, un `alt="PayTech"` le ferait annoncer deux fois par un lecteur d'écran. ⚠️ **Dimensions dans le HTML** : sans elles l'image réserve zéro pixel puis pousse le texte à son arrivée, juste sous le bouton qu'on vient de viser. ⚠️ **`flex: 0 0 auto`** : sans quoi le texte comprime le logo sur une carte étroite — une marque déformée est pire que pas de marque. Le service worker le met en cache sans configuration (`/**/*.png` y figurait déjà). — _F11.3._
- [x] **Une corbeille dans les espaces : ranger sans détruire.** Demande du client : *« parfois les onglets, on a tellement de choses et on veut alléger »*. Or la plateforme ne connaissait **aucun effacement différé** — pas une colonne `deleted_at`, pas un modèle en `SoftDeletes` : supprimer effaçait pour de bon, et l'on n'osait donc pas ranger. Périmètre arrêté avec lui : les **cinq annonces qui remplissent les onglets** (biens, véhicules, trajets, expériences, offres de nuitée), conservation **30 jours** avec compte à rebours visible, puis effacement définitif par tâche planifiée (`corbeille:purger`, 04h00). Les pièces jointes (photos, documents, certifications) restent en suppression immédiate — une corbeille qui avale aussi les petites pièces devient elle-même un fouillis à trier. ⚠️ **Deux notions à ne pas confondre, et le client l'a compris ainsi** : *archivé* = retiré du catalogue public mais toujours dans ma liste ; *corbeille* = retiré de ma liste, récupérable. La seconde ne remplace pas la première. ⚠️ **`DELETE /properties/{property}` N'EXISTAIT PAS** : un bien ne pouvait qu'être archivé, donc rester à vie dans la liste de son propriétaire — celui qui avait vendu trois biens en gardait trois lignes mortes pour toujours. C'est exactement le besoin exprimé. ⚠️ **LA RÈGLE DE SÉCURITÉ : ce qui revient de la corbeille revient ÉTEINT.** Un bien restauré ne redevient pas publié tout seul, il revient *archivé* — entre-temps il a pu être vendu, le véhicule accidenté, le prix devenir faux. Sans cette règle, une restauration remettrait des annonces en ligne à l'insu de tout le monde ; un test le verrouille en partant d'un bien **publié**. ⚠️ **Le socle avait DÉJÀ sa doctrine du retrait** (`OfferRetirementService`, F8.19 — « on ne supprime jamais une offre qui a servi », toute réservation même annulée interdisant l'effacement). La garde nouvelle a donc été **restreinte aux seuls biens**, que rien ne couvrait : poser une seconde règle « à peu près pareille » sur les trois offres de prestataire aurait créé deux vérités concurrentes. Un bien engagé — réservation en cours, mandat de gestion actif — est refusé **avec son motif**, un refus muet laissant le propriétaire sans issue. ⚠️ **UN DÉFAUT INTRODUIT PUIS CORRIGÉ, le plus instructif de la tranche** : `OfferRetirementService::retirer()` détruisait les fichiers photo **avant** d'appeler `delete()`. Le jour où ce `delete()` est devenu différé, l'offre partait à la corbeille **sans une seule image** et serait revenue vide, définitivement, alors que l'écran promet de la rendre intacte. Le ménage des fichiers est déplacé au seul moment où l'effacement devient irréversible : la purge. Un test le verrouille. ⚠️ **Le cloisonnement est recopié de la colonne réelle de chaque table, jamais deviné** : `owner_id` pour un bien, `provider_id` pour un véhicule, une expérience ou un trajet — et une nuitée n'en porte **aucun**, elle appartient au propriétaire de son bien par ricochet (avec `withTrashed()` sur la relation, sans quoi une nuitée dont le bien est lui aussi à la corbeille resterait introuvable et bloquée là pour toujours). ⚠️ **`deleted_at` est INDEXÉ** : `SoftDeletes` ajoute son filtre à *toutes* les requêtes de ces tables, catalogue public compris — l'écran le plus consulté du site. Côté écran : **un seul écran pour les cinq types** (une corbeille par onglet aurait remplacé une liste encombrée par cinq listes encombrées), monté dans les espaces **propriétaire** et **prestataire** seulement — un client ou une entreprise ne possède aucune annonce et n'aurait qu'une corbeille vide à vie. On n'y supprime rien : ranger reste le geste de l'écran d'origine, qui connaît ses règles et sait refuser. **9 tests neufs**, bâtis en créant l'annonce d'un **tiers** à côté de celle de l'appelant. **Deux tests existants ont dû changer** : ils vérifiaient la disparition physique de la ligne, ce que la corbeille abolit précisément. — _F11.4._

- [x] **La corbeille arrive dans l'espace client — et elle n'y supprime rien.** Le client, lui aussi, a des onglets qui s'allongent : demandes, réservations, discussions, notifications. ⚠️ **Mais ses objets ne lui appartiennent pas seul**, et c'est ce qui a décidé de toute la tranche : une demande est la file de travail d'un agent, une réservation est un **contrat** entre lui, Kaikun et un partenaire, un fil de discussion est supervisé par le support. Réutiliser le `SoftDeletes` de F11.4 aurait retiré la ligne des requêtes de **tout le monde**, back-office compris : le client aurait allégé sa liste en **effaçant une pièce de dossier** dont dépendent la comptabilité, le reversement au partenaire et le règlement d'un éventuel litige. D'où un mécanisme volontairement **distinct** : un **masquage personnel** (`hidden_at`), honoré uniquement par les listes du client — le back-office continue de tout voir. ⚠️ **Conséquence assumée et AFFICHÉE** : ces éléments n'ont **aucun compte à rebours**, là où une annonce affiche « supprimé dans N jours ». L'écran écrit « Conservé — rien ne sera supprimé », et son sous-titre change selon ce qu'il contient : promettre une purge qui n'aura pas lieu inquiéterait pour rien. ⚠️ **Le masque d'une DISCUSSION est posé sur le lien participant↔fil, jamais sur le fil** : un fil a plusieurs lecteurs, et le ménage du client ne doit rien retirer de la file de l'agent qui lui répond. ⚠️ **Ranger n'est pas se taire** : un message neuf **fait revenir** le fil rangé, automatiquement. Sans cette règle, la réponse d'un agent atterrirait dans un fil invisible et personne ne comprendrait le silence du client — elle est posée sur la **création d'un message** et non dans les contrôleurs, parce que quatre endroits en créent et qu'on l'aurait oubliée au cinquième. ⚠️ **On ne range que ce qui est terminé, vu ou lu** : demande clôturée, réservation terminée ou annulée, fil entièrement lu, notification déjà ouverte — un dossier vivant reste sous les yeux de la seule personne qui doit s'en occuper, et une réservation à venir **s'annule**, elle ne se cache pas. Chaque refus dit **son motif** ; le bouton n'apparaît même pas là où le serveur dirait non. ⚠️ **Le mot du bouton est « Ranger », jamais « Supprimer »** : lire « Supprimer » sur une réservation ferait croire qu'on efface un contrat. ⚠️ **Un dossier restauré revient TEL QUEL, statut compris** — à l'inverse d'une annonce, qui revient éteinte : il n'a jamais cessé d'exister pour Kaikun, y toucher réécrirait un contrat. **14 tests neufs**, dont le seul qui compte vraiment : *ranger ne supprime rien, la ligne reste entière en base et lisible hors de la liste du client*. **2 tests de F11.4 adaptés** (l'identifiant de la corbeille est devenu une chaîne — celui d'une notification est un UUID). — _F11.5._

- [x] **Chaque grande page reçoit une image de fond, et les pages filles en héritent.** Un composant unique (`shared/components/page-hero/`) remplace le bloc `.uni-hero` que **douze pages recopiaient**, et lui ajoute une image chargée depuis le back-office. Côté serveur, `App\Support\Heroes\HeroCatalog` déclare les bandeaux pilotables (`defaut`, les 10 univers, `contact`, `faqs`, `recherche` et ses 5 déclinaisons) ; y **ajouter une entrée suffit** à la rendre pilotable et lisible, sans migration ni retouche d'écran. ⚠️ **L'image et le texte n'héritent PAS de la même façon, et c'est la décision structurante de la tranche.** L'**image descend** la chaîne de parenté jusqu'au bandeau `defaut` : une seule photo par univers habille toutes les pages qui en dépendent. Le **texte, jamais** : un titre est écrit *pour* une page, et faire descendre « Des biens vérifiés » sur une liste filtrée afficherait un titre **faux** — pire que pas de personnalisation du tout. ⚠️ **La parenté est déclarée, pas déduite des points de la clé** : `recherche.nuitees` a pour parent `nuitees` (l'univers) et non `recherche`, un lien qu'aucune convention de nommage n'exprimerait. ⚠️ **L'héritage est résolu côté SERVEUR** et le frontend lit simplement l'entrée de sa clé : faire remonter la chaîne dans le navigateur l'aurait obligé à connaître la parenté des pages, c'est-à-dire à **dupliquer le catalogue** — et à le laisser diverger au premier ajout. ⚠️ **Une chaîne vide n'est pas un titre vide, c'est un RETRAIT de surcharge** : les textes des gabarits restent la valeur par défaut, la saisie back-office ne fait que passer devant quand elle existe. Il n'existe donc **aucun état dans lequel le back-office laisse une page sans titre**, y compris par omission — et une plateforme sur laquelle personne n'a rien saisi affiche exactement ce qu'elle affichait avant l'existence de cet écran. ⚠️ **La photo est posée sous un voile dégradé**, doublé d'une ombre portée sur le texte et d'un assombrissement des cartes de points forts : le bandeau écrit en **blanc**, et on ne peut pas faire confiance à la photo que l'équipe choisira — une plage ou une façade au soleil rendrait le titre illisible. ⚠️ **Les styles de la variante `--image` vivent dans le style GLOBAL** (`styles/_universe.scss`) et non dans la feuille du composant : le contenu propre à chaque page y est **projeté**, or sous encapsulation émulée une feuille de composant ne touche pas les nœuds projetés — la règle n'aurait rien atteint, en silence. ⚠️ **L'invitation « Contactez-nous » de la FAQ est sortie de l'accroche** : celle-ci est devenue une donnée réécrivable, et un texte saisi au back-office ne peut pas contenir de lien interne (un `routerLink` s'y afficherait tel quel). — _F12._

- [x] **La page catalogue s'ouvre enfin — et sur cinq visages, pas un.** `/recherche` porte désormais un bandeau dont le titre, l'accroche **et l'image** suivent l'onglet d'univers actif (clés `recherche.immobilier`, `recherche.nuitees`…). ⚠️ **Les textes sont écrits pour la page de RÉSULTATS, pas recopiés de la grande page de l'univers** : ici le visiteur a déjà choisi ce qu'il cherche, on l'aide à trier — on ne lui présente plus le métier. Quelqu'un qui cherche une villa à la nuit et quelqu'un qui cherche un 4×4 ne font pas la même chose ; les accueillir avec la même phrase générique était une occasion perdue. Sans saisie, chacun de ces cinq bandeaux **reprend la photo de son univers** : l'équipe charge cinq images et les dix pages sont habillées. — _F12._

- [x] **Un onglet « Bandeaux » au back-office (Paramètres & contenu).** Une fiche par page : aperçu de ce que le visiteur voit **réellement**, dépôt d'image, trois champs de texte facultatifs, retrait de la photo, réinitialisation complète. Permission `gerer:parametres` — même garde que le paramétrage, c'est du contenu de vitrine et non un dossier client. ⚠️ **L'écran distingue « photo propre » et « photo affichée »**, et c'est ce qui le rend lisible : une page qui hérite déjà de l'image de son univers porte la pastille **« héritée »**. Sans cette nuance, elle passerait pour « sans image » et l'équipe rechargerait la même photo sur chaque page. ⚠️ **Le bouton « Enregistrer » reste éteint tant que rien n'a bougé** : ouvrir un formulaire puis l'enregistrer sans y toucher écrirait une ligne en base et ferait passer un bandeau vierge pour personnalisé. ⚠️ **`POST` et non `PATCH`, `FormData` toujours** : PHP ne décode `multipart/form-data` que sur un POST (`$_FILES` reste vide sur un PATCH) — même piège que le justificatif de reversement. L'image est recompressée et **l'ancien fichier est supprimé du disque** au remplacement comme au retrait. **15 tests backend** (dont l'héritage, son asymétrie avec le texte, et le retour au texte d'origine) + **4 vitest**. — _F12._

- [x] **Le bandeau à l'épreuve de la première vraie photo — quatre défauts, tous invisibles au test et tous vus à l'écran.** La tranche F12 était verte ; le premier usage réel l'a démentie sur quatre points, ce qui est exactement ce à quoi sert une recette. ⚠️ **(1) On ne voyait plus la photo, mais un rectangle bleu.** Le voile de lisibilité était un aplat du **bleu de marque à 86 %**, uniforme : il *teintait* l'image au lieu de l'assombrir, et il l'assombrissait partout alors que le texte n'occupe que la gauche (titre borné à 18ch). Il est devenu un navy neutre **directionnel**, de 84 % à gauche à 8 % à droite. Il a fallu pour cela le **sortir du style en ligne** vers `.uni-hero--image::before` : un style en ligne **ignore les requêtes média**, or sur téléphone le texte prend toute la largeur et réclame un voile vertical, pas horizontal. ⚠️ **(2) Une image de fond n'est pas une photo d'annonce.** La borne commune de 1600 px convient à une vignette de 600 à 900 px, pas à un fond **étiré sur toute la largeur de l'écran** : le navigateur l'agrandit dès un moniteur de 1920 px, donc floute. Bornes propres aux bandeaux : **2560 px / JPEG 88**. ⚠️ **(3) Rien ne pouvait rattraper une photo déposée trop petite** — `scaleDown` réduit, il n'agrandit jamais. Constaté : une vignette de **360 × 360 px** posée en fond de page. Le dépôt exige désormais **1400 × 500 px** au minimum ; le refus est prononcé **deux fois**, au serveur (autorité) et dans le navigateur **au moment du choix du fichier**, sous le bouton même — car le message d'erreur de cet écran est unique pour toute la page et s'affiche en haut, hors de vue quand on choisit son image parmi vingt fiches. ⚠️ **(4) L'équipe déposait dix photos et n'en voyait qu'une.** `HeroService` partage sa liste entre les douze pages publiques, mais « une seule fois » voulait dire **une seule fois pour la vie de l'onglet** : les images chargées après l'ouverture de l'application n'arrivaient qu'après un rechargement complet du navigateur, geste qu'une application d'une seule page ne demande jamais. Le service expose `refresh()`, appelé après chaque enregistrement, retrait et réinitialisation. ⚠️ **Le déclencheur est un `Subject` + `startWith`, pas un signal via `toObservable`** — ce dernier n'émet que depuis un **effet**, donc au premier cycle de détection et non à la construction : la première requête cessait de partir au montage, ce que les tests ont pris sur le fait. **87 vitest + 15 tests backend.** — _F12.1._

- [x] **Une carte sans marges, et une classe CSS qui n'existait pas — le même piège d'encapsulation, deux fois.** Le dépôt de dossier de chantier (page Construction) s'affichait **texte collé aux bords**, sans espacement des champs. Cause : les règles `.lead-form` vivaient dans la feuille du composant `app-lead-form`, alors que `construction-request-form` **reprend délibérément ces classes** ; sous encapsulation émulée, une feuille de composant ne touche que les éléments écrits dans SON gabarit — les règles n'atteignaient donc rien, **sans erreur ni avertissement de compilation**. Elles sont passées dans `styles/_conversion.scss`. ⚠️ **C'est le troisième cas du même genre** (après `.uni-hero` et son contenu projeté) : *une classe portée par plus d'un composant est un style GLOBAL*, la règle est désormais écrite en tête du README frontend. ⚠️ **Dans la même carte, `.k-hint` était employée sans avoir JAMAIS été définie** — nulle part dans le projet, alors que deux gabarits s'en servent. Un sélecteur absent ne lève rien : l'explication sous le champ s'affichait en corps de page, aussi noire et aussi grosse que le contenu qu'elle accompagne. Définie dans `_base.scss`, aux côtés de `.k-error`. — _F12.1._

### Phase F13 — Les graphiques du business, au back-office

Demande du client : le back-office savait **tout compter et rien montrer**. Il
affichait des compteurs (« 12 biens en attente ») ; il ne traçait aucune
évolution. Or personne ne pilote une entreprise sur un compteur — on la pilote
sur une tendance.

- [x] **Une rubrique « Statistiques » dédiée, et non des graphiques ajoutés à la Vue d'ensemble.** Les deux écrans répondent à des questions de rythme différent : la Vue d'ensemble s'ouvre **chaque matin** (ce qui attend, ce qui alerte, ce qu'on traite aujourd'hui), Statistiques se consulte **en fin de mois** (des tendances sur des mois). Les mélanger aurait allongé l'écran opérationnel de contenus qu'on fait défiler sans les lire, et noyé les files d'attente qu'on vient justement y chercher. Six chiffres d'en-tête (chacun comparé à la période précédente), puis six visuels : **revenus dans le temps** (volume brut + commission), **d'où vient l'activité** (réservations par univers métier, en colonnes empilées), **tunnel commercial** (demande → devis → réservation → prestation honorée, avec le taux de passage entre chaque étage), **où en sont les réservations** (part-à-tout des statuts) et **ce qui rapporte le plus** (palmarès des annonces). ⚠️ **Un seul filtre de période, en haut, qui cadre TOUT** : un filtre par carte aurait permis d'afficher côte à côte un chiffre d'affaires sur douze mois et un nombre de réservations sur trente jours — deux vérités qui, mises l'une à côté de l'autre, en fabriquent une fausse. — _F13.1._

- [x] **Gardée par `gerer:paiements`, pas par la permission de base du back-office.** L'écran consolide chiffre d'affaires, commission et panier moyen : c'est la vue la plus financière du produit, et le CDC §7 borne l'agent Kaikun à un « accès financier limité ». Tout ce qui touche à l'argent (Paiements, Reversements) passe déjà par ce droit ; une permission dédiée aurait fabriqué une troisième porte sur le même coffre. ⚠️ L'argument « c'est en lecture seule, donc c'est ouvert » a été écarté : **on ne protège pas un chiffre en interdisant seulement de le modifier.** — _F13.1._

- [x] **Aucune bibliothèque de graphiques : du SVG écrit à la main.** Une bibliothèque impose son allure, qu'il faut ensuite combattre pour retrouver la charte ; Chart.js dessine dans un `<canvas>` qui ne rend **rien au rendu serveur**, actif sur ce projet ; et la rubrique entière, six graphiques compris, pèse **40 ko** (10 ko compressés) — moins qu'une bibliothèque seule. ⚠️ **Les couleurs sont MESURÉES, pas choisies à l'œil** : la palette a été passée à un validateur sur le fond réel des cartes — séparation sous protanopie/deutéranopie (pire paire voisine ΔE 8,1 pour un seuil de 8), vision normale (15,1 pour un plancher de 15), contraste au-dessus de 3:1 partout. **Deux teintes de la charte ont dû être assombries** : l'or `#d3ae52` ne tenait que 2,11:1 sur blanc et le rose `#e87ba4` 2,69:1 — une part de graphique à 2:1 est une part qu'on devine plutôt qu'on ne la voit. ⚠️ **L'ORDRE de la palette fait partie de ce qui est validé**, car c'est lui qui rend distinguables deux univers voisins dans une pile ; il est figé côté serveur, si bien qu'**une couleur suit un métier et jamais son rang du moment**. ⚠️ **Chaque graphique a sa vue tableau** (bouton « Données ») : un dessin encode par la position et la couleur, ni l'une ni l'autre n'étant disponible à qui navigue au lecteur d'écran — et l'équipe y recopie un chiffre exact, là où le graphique ne donne qu'un ordre de grandeur. — _F13.1._

- [x] **Trois pièges de calcul traités côté serveur.** ⚠️ **(1) Les mois vides.** Une agrégation SQL ne renvoie que les mois où il s'est passé quelque chose : tracer directement dessus relierait juillet à septembre **en sautant août**, dessinant une pente régulière là où il y a un trou. L'axe est fabriqué d'abord, les valeurs y sont versées ensuite ; un mois vide vaut zéro et se voit comme tel. ⚠️ **(2) La portabilité.** `DATE_FORMAT` est du MySQL, `strftime` du SQLite : le projet tourne sur l'un et teste sur l'autre, un agrégat qui ne s'exécuterait que sur MySQL serait un agrégat **non testé**. L'expression est choisie par driver. ⚠️ **(3) Sept cibles polymorphes, cinq couleurs.** Afficher les sept types réservables donnerait sept séries, au-delà du seuil où l'œil sépare deux teintes voisines : on regroupe en cinq **lignes de métier**, qui sont de toute façon la maille à laquelle un dirigeant raisonne — un véhicule de location et un départ programmé sont un seul métier, même s'ils font deux tables. ⚠️ **Règle de calcul unique** : un **montant** ne compte jamais une réservation annulée, mais un **dénombrement** les compte toutes — sinon le taux d'annulation, indicateur de santé à part entière, serait nul par construction. **8 tests backend + 5 vitest.** — _F13.1._

- [x] **Trois défauts vus à l'écran, aucun visible aux tests.** La tranche était verte ; la première capture l'a démentie. ⚠️ **(1) Le graphique principal s'affichait VIDE**, ses seules pastilles de fin flottant dans le blanc. L'état masqué de l'animation d'entrée (`stroke-dashoffset: 1`) vivait sur la **règle de base** du tracé au lieu du `from` de l'animation : la courbe ne réapparaissait donc que si l'animation se jouait — et elle ne se joue ni au rendu serveur, ni quand le navigateur ou une extension coupe les animations. Règle générale retenue : **l'absence d'animation doit donner le graphique tracé, jamais le graphique absent.** ⚠️ **(2) La sixième tuile tombait seule sur une deuxième ligne**, orpheline sous cinq voisines : la grille automatique a été remplacée par une grille explicite, une rangée d'indicateurs se lisant d'un seul balayage. ⚠️ **(3) Les variations se coupaient en trois fragments** (« +43,4 » / « % » / « vs 12 mois » / « précédents ») dans une tuile étroite. Rien de tout cela n'était détectable autrement qu'en regardant : un graphique ne se juge pas au test. — _F13.1._

- [x] **La recette de F13.1 : deux défauts, tous deux liés à des données que la démonstration n'avait pas.** ⚠️ **(1) La tuile de tête écrasée à 75 px de large.** Sur une plateforme sans historique avant la fenêtre analysée, les six tuiles affichent toutes le message de repli « Première activité sur ce poste » — cas absent des données de démonstration, qui avaient toutes une période précédente. Or le `white-space: nowrap` posé sur le paragraphe de variation (pour empêcher « +43,4 » de se séparer de son « % ») rendait aussi cette **phrase longue insécable** : chaque tuile imposait dès lors sa largeur en minimum à sa colonne de grille, et la tuile de tête — seule assez compressible pour céder, son contenu se coupant en plusieurs lignes — absorbait tout l'écrasement. L'insécabilité est descendue sur les **fragments** concernés. Au passage, la grille est passée de sept colonnes (chiffre d'affaires sur deux) à **six, puis trois, puis deux** : ces trois nombres divisent six exactement, donc plus jamais de case vide en fin de rangée, et surtout des colonnes assez larges pour un montant en francs une fois le rail du back-office déduit. La tuile de tête se distingue désormais par sa couleur et la taille de son chiffre, ce qui suffit à la hiérarchie. ⚠️ **(2) La courbe sortait de sa carte par le haut**, passant derrière le bouton « Données ». L'axe s'arrêtait à 4 M pour un volume de 5 508 000 F : `niceTicks` générait les graduations *jusqu'au dernier multiple sous le maximum* au lieu du **premier au-dessus**, et l'appelant se sert de la dernière graduation comme échelle. Le tracé était juste, l'axe était faux. Même cause en attente sur les colonnes empilées, où le filtrage des graduations non entières *après coup* jetait aussi le sommet de l'échelle — `niceTicks` reçoit désormais l'exigence d'entiers et l'applique au **pas**. Du calcul pur, donc verrouillé par des tests (`chart-tokens.spec.ts`, dont le cas exact de la recette). **100 vitest.** — _F13.1.a._

- [x] **Trois ajustements demandés par le client après essai (F13.2).** ⚠️ **(1) Le filtre commence désormais aux jours courts** : 7, 15 et 30 jours avant les 6 et 12 mois. Le pas reste choisi par le serveur (jour pour les trois premiers), et la formule de comparaison sous chaque indicateur est maintenant **dérivée du libellé de la période** au lieu d'une liste de cas écrite côté frontend — la liste, précisément, s'était trompée à l'ajout de 7 et 15 jours en annonçant « vs 12 mois précédents ». ⚠️ **(2) « Ce qui rapporte le plus » devient un diagramme circulaire**, placé à côté de « Où en sont les réservations », le tunnel commercial passant en dernier sur toute la largeur. Deux règles rendent ce disque honnête : les cinq annonces de tête ne faisant pas tout le chiffre d'affaires, une part **« Autres annonces »** calculée par différence **ferme le disque** — sans elle les parts totaliseraient 100 % d'un ensemble qui n'est pas le tout, ce qui exagérerait mécaniquement le poids des premières ; et parce que **l'œil compare mal des angles**, chaque part est chiffrée dans la légende (montant et pourcentage). Les couleurs suivent une **rampe ordinale d'une seule teinte**, du foncé au clair : un classement est ordonné, la couleur porte donc le rang, et non cinq identités. Le gris du « reste » est hors rampe — cet agrégat n'a pas de rang. La rampe est validée (clarté strictement décroissante, écarts visibles, extrémité claire à 2,11:1) et ne compte que **cinq paliers** : une sixième marche ne tient pas dans la plage utilisable, ce qui fixe le palmarès à cinq entrées côté serveur. ⚠️ **(3) La rubrique Statistiques passe juste après Vue d'ensemble** dans le rail : les deux prolongent le même module 1 du CDC §6 et se lisent ensemble — l'une dit ce qu'il y a à faire aujourd'hui, l'autre où va l'entreprise. Le voisinage par le sujet l'emporte sur le voisinage par le droit (elle partage `gerer:paiements` avec Paiements et Reversements, près desquels elle était d'abord rangée) ; le rail restant filtré par les permissions, ce déplacement n'ouvre l'écran à personne de nouveau. **102 vitest.** — _F13.2._

- [x] **Les tuiles d'indicateurs prennent chacune leur couleur (F13.3), à la demande du client.** Un liseré supérieur et une pastille d'icône teintée par tuile ; le chiffre et le libellé, eux, **restent en encre** — une valeur écrite dans une couleur claire se lit mal, et c'est le chiffre qu'on vient chercher. ⚠️ **Ces teintes ne codent rien**, et c'est assumé : chaque tuile porte son libellé en toutes lettres, la couleur n'est qu'un repère pour retrouver « la tuile violette » d'un coup d'œil. Elles échappent donc aux contrôles de séparation qu'on impose aux séries de données — mais pas au **contraste**, mesuré sur le fond blanc (4,03 · 5,24 · 6,22 · 5,05 · 3,34 pour 1, tous au-dessus du seuil de 3:1). ⚠️ **Elles sont volontairement PRISES HORS de la palette des graphiques** : sur cet écran le bleu de marque veut déjà dire « Nuitées » et l'orange « Mobilité » ; reprendre ces teintes sur les tuiles aurait suggéré un lien entre une tuile et un univers métier — un lien qui n'existe pas. D'où un teal, un indigo et un violet, absents des séries. Deux exceptions qui portent bien du sens : le **rouge** du taux d'annulation (l'indicateur est mauvais quand il monte) et l'**or**. — _F13.3._

- [x] **Les files de validation tiennent sur une seule ligne, en cinq couleurs (F13.4), à la demande du client.** La grille de la Vue d'ensemble comptait quatre colonnes pour **cinq** files : la cinquième — les prestataires — tombait seule sur un deuxième rang, large comme un quart d'écran, et se lisait comme une catégorie à part alors que c'est une file comme les autres. Cinq colonnes explicites, tuiles resserrées, puis trois par ligne sous 900 px. Chaque tuile porte sa teinte par une seule variable (`--q`) dont découlent le liseré, le fond, le halo, le chiffre et le libellé. Animation d'entrée en cascade de gauche à droite, et au survol la tuile décolle pendant que son liseré s'épaissit. ⚠️ **L'état masqué vit dans le `from` des `@keyframes` avec `backwards`, jamais sur la règle de base** — c'est exactement le défaut qui avait affiché une courbe vide en F13.1 ; `prefers-reduced-motion` coupe le mouvement en gardant la couleur. ⚠️ **Ici les teintes SONT celles de la palette des graphiques, à rebours du choix de F13.3** — et pour la même raison de fond. Sur l'écran Statistiques, le bleu voulait déjà dire « Nuitées » : le reprendre sur une tuile aurait suggéré un lien inexistant. Sur la Vue d'ensemble il n'y a aucun graphique, donc aucune convention concurrente ; et surtout ces cinq couleurs distinguent **cinq catégories réelles**, ce qui est précisément le travail d'une palette catégorielle. La réutiliser évite d'inventer — et de devoir revalider — une sixième famille de couleurs pour le même back-office. — _F13.4._

- [x] **La vitrine de l'accueil passe les cinq univers en revue (F13.5), à la demande du client.** Elle ne montrait que l'immobilier : le tourisme et le transport, qui portent une bonne part de la promesse, n'apparaissaient nulle part sur la page d'accueil. Elle change d'univers **toutes les 7 secondes**, six cartes à chaque fois, avec des pastilles cliquables pour aller droit au but ; le titre suit ce qui est montré (« Des circuits vérifiés, prêts à partir »), car un titre unique mentirait au-dessus d'une grille de véhicules. ⚠️ **Chaque univers n'est chargé qu'une fois puis mis en cache, et le suivant est préchargé** pendant qu'on regarde le courant : sans cela une vitrine qui tourne indéfiniment rappellerait l'API tant que l'onglet reste ouvert, et chaque bascule montrerait un chargement. ⚠️ **Les univers sans annonce sont retirés du tour** — sur une plateforme qui démarre, c'est le cas normal, et la vitrine s'arrêterait sinon sur « Le catalogue s'enrichit » devant un client. ⚠️ **Le minuteur ne tourne pas au rendu serveur** (une horloge qui bat toutes les sept secondes empêche le SSR de se stabiliser) et s'arrête à la destruction du composant. ⚠️ **Deux défauts de mise en pause trouvés à l'usage** : la pause au survol couvrait toute la section — haute de deux rangées réservées — si bien qu'une souris posée n'importe où dans ce vide gelait le tour ; et suspendre sur tout `focusin` figeait la vitrine **définitivement** après un clic, puisqu'un clic laisse le bouton focalisé et que `focusout` peut ne jamais venir. La pause ne porte plus que sur les pastilles et les cartes, le focus ne compte que s'il est **clavier** (`:focus-visible`), et un garde-fou repart au bout d'une minute de pause. Au passage, l'onglet actif du moteur de recherche cessait d'être bleu au survol : `.search-tab:hover` compte une classe de plus que `.search-tab--active` et l'emportait quel que soit l'ordre — le libellé blanc tombait à **1,14:1** de contraste sur le bleu pâle. — _F13.5._

- [x] **Les fiches montrent enfin la photo de l'annonce, et deux bandes navy s'arrondissent (F13.6).** Le bandeau de titre d'une fiche était un dégradé de marque, les photos n'apparaissant qu'en galerie plus bas : le visiteur arrivait sur une page qui ne ressemblait pas à la carte sur laquelle il venait de cliquer. Le bandeau porte désormais **la photo principale** — la même que la couverture du catalogue — et vaut pour **les cinq univers d'un coup**, puisqu'il vit dans la coquille partagée `app-detail-layout`. Sans photo, le dégradé d'origine reste. ⚠️ **Une balise `<img>` et non un fond CSS** : un fond n'est découvert qu'après la feuille de style et le calcul de style, or c'est le plus grand élément peint de la page ; en balise il est trouvé dès la lecture du HTML et porte `fetchpriority="high"`. ⚠️ **Le voile de lisibilité est MESURÉ** : n'importe quel prestataire peut déposer n'importe quelle image, le contraste doit donc tenir sur une photo **entièrement blanche**. La première version (0,45 en haut) ne donnait que **2,32:1** au fil d'Ariane — placé tout en haut, là où le voile est le plus léger ; les valeurs retenues donnent **6,55:1** au titre et **4,53:1** au fil d'Ariane dans ce pire cas. Enfin, les sections « Protocole de confiance » et « Kaikun 360 en chiffres » sont **décollées des bords et arrondies**, dans la continuité des surfaces arrondies de F11.1 : les deux surfaces navy de l'accueil se répondent, au lieu que l'une soit une carte et l'autre un trait en travers de l'écran. Le pied de page, lui, reste pleine largeur — c'est un composant partagé par tout le site. — _F13.6._

### Phase F14 — Ouverture officielle : liste d'attente et fermeture d'accès ⚠️ **HORS CAHIER DES CHARGES**

Deux demandes directes du client (2026-08-14), en marge du CDC : il maintenait
lui-même une page « Bientôt disponible » sur le domaine public pour constituer
une masse critique d'inscrits avant l'ouverture, et voulait pouvoir fermer
toute la plateforme au public le temps de la préparer, sans en priver son
équipe.

- [x] **La liste d'attente, détachée de la page du client, à 5 profils au lieu de 3.** La page que le client maintenait lui-même (hors de ce dépôt) ne couvrait que Propriétaire/Prestataire/Client ; celle-ci ajoute **Team building** et **Diaspora**, chacun avec ses propres champs (`details`, colonne JSON — même convention que `team_building_requests.needs`). ⚠️ **Aucun des flux de demande existants n'était réutilisable** : `requests`, `team_building_requests`, `diaspora_projects` exigent tous une session authentifiée avec `user_id` — un prospect n'a pas encore de compte. Le seul patron réellement anonyme du projet était **Contact** (F2.8.1), suivi de bout en bout : dépôt public (`POST /waitlist`, throttle 10/min), alerte e-mail à l'équipe, aucun écran de consultation pour l'instant (reporté, l'équipe suit par e-mail en attendant). **Route interne `/liste-attente`, volontairement pas encore liée à la navigation ni au domaine public** — la bascule reste une décision du client. 10 tests backend, 5 vitest.

- [x] **La fermeture d'accès avant ouverture, un interrupteur et non une refonte.** Le client veut pouvoir montrer la plateforme à une poignée de personnes de confiance pendant qu'il la prépare, sans l'exposer au public ni priver son équipe de travailler. Un réglage back-office (`platform.gate_enabled`, décoché par défaut) ferme **toute l'API** sauf une liste blanche courte et explicite (back-office, connexion, liste d'attente, contact, FAQ, pages légales) — quiconque d'autre, visiteur ou compte client/propriétaire/prestataire/entreprise, reçoit une redirection vers la liste d'attente. ⚠️ **Le back-office n'est jamais concerné**, quel que soit le réglage : l'équipe continue de travailler normalement. ⚠️ **L'octroi individuel se fait sur un compte existant** — une case « Accès anticipé » sur la fiche compte du back-office, réservée au **super administrateur seul** (même garde que l'attribution des rôles d'administration), qui accorde une permission Spatie **directe** (`acces:plateforme`), jamais portée par un rôle public. Le super_admin, lui, passe toujours via `Gate::before`, sans avoir à être nommé nulle part dans la logique du garde. ⚠️ **Piège rencontré** : un test qui comptait les requêtes SQL du catalogue (B17.4) s'est mis à échouer, non pas à cause d'un coût par ligne mais parce que ce nouveau garde, appliqué à **toute** l'API, réchauffe le cache des réglages au premier appel du test — corrigé en préchauffant ce cache dans le test, pas en modifiant le garde. **9 tests backend neufs**, **5 vitest neufs** (garde de navigation).

- [x] **L'écran back-office de consultation de la liste d'attente, puis l'invitation automatique du prospect.** Une inscription n'était jusque-là visible nulle part au back-office (elle n'a pas de compte, donc pas de fiche dans l'annuaire) — seule trace, l'e-mail d'alerte à l'équipe. Écran `/back-office/liste-attente` (liste filtrable par statut/catégorie + fiche détail restituant **tous** les champs saisis par le prospect, y compris ceux propres à sa catégorie), gardé par `traiter:demandes` — même patron que la file des messages de contact. Marquer une inscription « traitée » enregistre l'agent et l'horodatage, **et déclenche l'envoi d'une invitation par e-mail au prospect** (s'il a laissé une adresse — le formulaire n'exige que le téléphone) : contenu entièrement différent selon ses 5 catégories, bouton vers l'inscription. ⚠️ **Destinataire sans compte** : premier e-mail du projet envoyé par routage anonyme plutôt qu'à un `User`. ⚠️ **La bascule seule déclenche l'envoi** (`nouveau → traité`), jamais une confirmation d'un statut déjà traité ni un retour à « nouveau » — sinon l'e-mail partirait en double. ⚠️ **Ce que cet e-mail ne fait pas encore** : il n'accorde pas lui-même l'« Accès anticipé » du point précédent — un super admin doit toujours le cocher séparément sur le compte que le prospect créera. **13 tests backend neufs**, suite complète verte (**1095 tests / 3876 assertions**).

### Infrastructure — Conteneurisation Docker et intégration continue ⚠️ **HORS CAHIER DES CHARGES**

Premier des trois chantiers de déploiement convenus avec le client (2026-08-14) :
CI d'abord, Docker ensuite, publication sur le VPS Contabo en dernier. Cette
tranche couvre les deux premiers.

- [x] **Sept services Docker, testés de bout en bout en local.** `mysql` ·
  `redis` · `backend` (API Laravel, PHP-FPM) · `scheduler` (`schedule:work`,
  sans lequel aucune réservation ne se clôture ni aucun reversement ne part) ·
  `queue-worker` (`queue:work`, les e-mails/notifications) · `frontend`
  (Angular en **SSR**, jamais un `dist/` statique) · `nginx` (point d'entrée
  unique — `/api`, `/storage`, `/sitemap.xml` vers le backend, le reste vers le
  frontend, exactement le découpage du proxy de développement). Détail complet
  et **cinq pièges Docker/MySQL/nginx résolus** (PHP 8.4 imposé par le lock
  malgré `^8.3`, client `mysql` absent des images Alpine, TLS, plugin
  d'authentification, cache DNS nginx figé sur l'ancienne IP d'un conteneur
  recréé) dans `docker/README.md`. Vérifié en conditions réelles : inscription
  complète (écriture MySQL, rôle assigné, jeton émis), e-mail transactionnel
  consommé par le worker via Redis, page d'accueil rendue en SSR, image servie
  par `/storage`.
- [x] **`DatabaseSeeder` tourne au démarrage du conteneur `backend`, jamais les seeders de démonstration.** Sans les rôles/permissions, la première inscription échoue en 500 (`RoleDoesNotExist`) — ce seeder est indispensable au fonctionnement, pas une commodité de développement. Idempotent, donc rejoué sans risque à chaque redémarrage.
- [x] **Un vrai bug de production démasqué, pas un défaut Docker.** Premier
  regard jamais posé sur le build de production (`server.mjs`) dans un
  navigateur réel — jusqu'ici le site n'était vu qu'à travers `ng serve`
  (dev). La mise en page était intégralement cassée (liens soulignés partout,
  styles quasi absents) alors que le CSS se chargeait bien (`200`, bon
  `Content-Type`, octet pour octet identique). Cause : la CSP durcie de
  `server.ts` (revue de sécurité 2026-08, `script-src` sans `'unsafe-inline'`,
  délibérément) bloque le `onload` **inline** qu'Angular pose par défaut en
  production pour charger le CSS non critique de façon asynchrone
  (`<link media="print" onload="this.media='all'">`) — la feuille reste donc
  en `media="print"` pour toujours, jamais appliquée à l'écran. Corrigé sans
  affaiblir la CSP : `angular.json → production.optimization.styles.inlineCritical: false`, Angular émet alors un `<link>` synchrone classique.
- [x] **CI GitHub Actions, deux jobs indépendants.** `backend` (PHP 8.4, service MySQL, `php artisan test`) et `frontend` (Node 24, `npm test` — le nouveau lanceur vitest d'Angular 22 tourne seul par défaut, pas de flag `--watch` à ajouter —, puis `npm run build` en configuration production). ⚠️ **Pint volontairement absent de la CI** : `./vendor/bin/pint --test` échoue aujourd'hui sur ~130 fichiers préexistants — l'inclure ferait échouer CI sur du code sans rapport avec ce qui vient d'être écrit.
- [x] **Publié sur le VPS Contabo réel (2026-08-15), pas seulement en local.** Monorepo cloné via une **Deploy Key GitHub dédiée en lecture seule** (jamais les identifiants personnels), `docker compose up --build` sur les sept services. Vérifié de bout en bout sur l'IP publique du serveur : inscription complète (écriture MySQL, jeton émis), page d'accueil rendue en SSR, CSS chargé normalement. ⚠️ **Sixième piège trouvé, propre à toute adresse publique non-`localhost`** : le serveur SSR Angular embarque une protection anti-SSRF qui **rejette en 400 tout en-tête `Host` non explicitement autorisé** — invisible en local (toujours `localhost`), bloquant sur IP ou domaine réel. Corrigé par la variable `NG_ALLOWED_HOSTS` (voir `.env.docker.example` et `docker/README.md`), **à tenir à jour à chaque changement d'adresse publique** (IP de test → sous-domaine → `kaikun360.com` au jour de la bascule).
